## 二、开发准备

### 1、系统提示词

#### 什么是系统提示词？
为了规范大模型的行为要求准则，我们通常需要在提示词内设定规范，为了不要每次对话都手动输入这类提示词，因而引入了“系统提示词“，每次的对话请求都会默认将这部分的内容作为提示词的一部分传输给服务器作为上下文交互。因为不同的项目对于模型开发的限定会不一样，因此也会有支持全局（即整个工具维度，不限项目）or 支持制定项目范围的系统提示词。

以下是从知乎上找到的各类工具/平台的系统提示词。
![alt text](image.png)

我们可以看到，不同平台都有属于自己的系统提示词命名方式，在这个背景下，openai 和 google 联手统一了一个简单的开放标准：AGENTS.md (claude code 似乎不支持)。这个文档也很简单，就是一个 markdown 的文件，openai 提供的官方示例：（主要是规范了开发环境、测试说明、代码拉取请求要求说明等等，瞅瞅是啥就行了）

```markdown
# Sample AGENTS.md file

## Dev environment tips
- Use `pnpm dlx turbo run where <project_name>` to jump to a package instead of scanning with `ls`.
- Run `pnpm install --filter <project_name>` to add the package to your workspace so Vite, ESLint, and TypeScript can see it.
- Use `pnpm create vite@latest <project_name> -- --template react-ts` to spin up a new React + Vite package with TypeScript checks ready.
- Check the name field inside each package's package.json to confirm the right name—skip the top-level one.

## Testing instructions
- Find the CI plan in the .github/workflows folder.
- Run `pnpm turbo run test --filter <project_name>` to run every check defined for that package.
- From the package root you can just call `pnpm test`. The commit should pass all tests before you merge.
- To focus on one step, add the Vitest pattern: `pnpm vitest run -t "<test name>"`.
- Fix any test or type errors until the whole suite is green.
- After moving files or changing imports, run `pnpm lint --filter <project_name>` to be sure ESLint and TypeScript rules still pass.
- Add or update tests for the code you change, even if nobody asked.
## PR instructions
- Title format: [<project_name>] <Title>
- Always run `pnpm lint` and `pnpm test` before committing.
```

### 2、Skill & MCP

#### 1）什么是SKill
当我们在进行不同项目&功能的具体开发时，可能很多抽象出来的特定流程、方法论，其实是可以抽象出来的，例如我们可能会对一个项目有“需求洞察-需求整理-功能设计-系统架构设计-技术选型-代码开发-功能测试-安全性检测“这样的流程设定，这类可以被复用且具有特定业务特定场景知识的内容便被整理成了大模型的技能包SKILL.md（因为 skill 的用途还是很广泛的，因此后续会专门开一个文档来说明skill的原理和构造）。

对比MCP：经常会看到MCP这个名词，MCP解决的是大模型外部数据源获取的问题，就是一系列设定好的输入输出（接口）规则，大模型可以通过约定的规范提供MCP需要的输入信息，并获得对应的数据返回以用于流程的推进和决策

#### 2）关于SKill 的安装 & 调用
目前我了解到的 skill的安装方式有3 种（其实就一种，让大模型帮安装）：
- 1、针对 skill plugin（技能包）：可以根据 github 上提供的安装方式，让大模型阅读后安装；
- 2、针对单个 skill：可以手动下载单个 skill 文件放到根目录的 skills 文件夹下；
- 3、使用skill installer 命令（/唤出），直接告诉大模型安装即可；

调用 skill 的方式：
- 1、自然语言：用自然语言和大模型对话，每次对话请求工具（vscode、claude code 等）都会将所有的 skill 说明作为上下文进行交互，大模型会根据对话要求分析后判断是否有匹配场景的 skill 可以使用，如果大模型计划调用 skill 功能，则其会在返回时询问是否要调用对应 skill。
- 2、手动调用：使用/来调用工具，可以唤起列表，选择后即可调用对应 skill，高亮展示的 skill 点击后还可以阅读其内容（vscode 是支持的）

### 3、需求准备

**1、需求挖掘**
- **目标**：此阶段主要是挖掘想法背后的真实需求，和AI 讨论需求的真伪，以及完善自己的想法，找到真实存在的需求，并围绕需求整理出需要做的事情；
- **具体操作**：无论是一个想法抑或是一个有较为明确要求的需求，我们都可以使用AI 协助完成需求的挖掘梳理。我们可以将自己的想法和要求尽可能地整理表达后，再让AI 协助我们完成需求的梳理，这里可以直接对话，或者使用superpowers/brainstorming 的 skill 来协助完成，区别就是skill 的追问会按照设计的流程，可能比直接对话追问更成体系更规范一些；

**2、需求规划（重要！）**
- **目标**：当明确需求和要做的事情后，需要对一系列的事项进行规划，类似于传统移动互联网的分版本迭代开发机制，确保最小mvp 产品的快速上线，以及抓住核心的主线推进。（因 vibecoding 是一个人代替一个团队来做事情，但交付的结果质量不变，严格规定范围和节奏可以尽量避免陷入无限的落地细节中所导致的项目迟迟无法上线的问题。）
- **具体操作**：将围绕核心需求的核心流程 & 最底层的核心竞争力能力抽出，作为mvp 的版本功能内容，其他的扩展、用户体验等相关的内容可以分多个版本进行规划落地，我觉得使用AI 的 coding 一般 2-3 天可以设定一个小版本，每次的功能迭代可以不超过 5 个，这样AI可以保证质量地完成版本功能的开发，又留有一定的时间修复和解决遇到的问题。（当然如果精力和经验丰富，可以自行调整，毕竟AI节约的是执行的事件，思考的快与慢，每个人的节奏和习惯都不一样）

> 注：实际也可以一次性做很多的功能，让AI 连续执行几个小时的任务，但做的功能越多，需要等待、验证、调整的时间也会越久，很难在落地过程中持续保持心流的状态，可能会造成个人对项目失去控制的感觉，此流程仅为个人的推进习惯；

**3、产品设计**
- **目标**：完成前端样式的设计工作，提供设计稿 & 原型图；
- **具体操作**：
  - 1）抄别的项目：可以直接截图丢给 ai 让其进行复刻；如果进一步需要调整的话，可以选择使用 pencil 插件 or figma 工具，将其他优秀的项目截图丢给 ai 并使用对应 mcp 工具复原页面，在其基础上进行微调后再让 ai 根据对应的稿子来执行。
  - 2）自己设计：可以通过手绘+文字标注说明的方式发给 ai，让其完成页面内容的布局理解和设计；

**4、拆解实施计划（重要！！！）**
- **目标**：使用AI 对每个版本的功能进行行动计划，明确具体需要做的事情，并区分优先级，确定工作细节，最终输出详细的需求文档&开发文档。（类似需求评审 & 开发思路对齐，这是最重要的一步，如果整体执行思路和方案有误，整体的代码实施就会跑偏，这里的确认直接影响 vibecoding 的最终效果）
- **具体操作**：同需求挖掘一样，可以直接对话，或者使用superpowers/writing-plans 的 skill来实现。这里会将需求拆解为详细的实施思路，包括使用的技术栈、功能的实施细节等等，跟着ai提供的信息进行确认/对话调整，以符合你自身的需求即可。这里可以大幅提升需求完成质量的注意事项有以下几点：（实际做商业项目时可考虑参考，个人简单的小项目可以优先按照自己的思路落地）：
  - 1）为保证需求拆解的完整性，可以尝试使用多个AI互相博弈的方式来不断完善需求文档，让多个AI 对对方的输出进行需求评审和开发评审，直到最后大家对方案达成一致后，确定最终的，没有任何歧义的需求开发文档，最后以 markdown 的形式输出。
  - 2）针对前端的项目，为保证视觉的统一性，可以让AI使用表格、流程图、ASCII 原型图来进行表达，以可视化的方式方便沟通理解。
  - 3）遇到看不懂的技术术语，可以新开一个对话框边问边学，确保自己能够看懂 ai 计划如何去做的思路，这样才能确保交付的内容和想要的是同一个东西。

## 三、项目开发 & 调试 & 部署

**1、项目开发：**
- **工作流建设**：建设一套自己方便的开发工作流模式，我使用的是 vscode 作为主开发工具（所有思考、主项目代码编写），antigravity 作为辅助工具（分析代码结构、调整前端样式、解答问题/学习）。
- **开发内容记录**：为了保证上下文内容不要太长，因此定期可以对改动点进行整理，一方面便于对改动版本进行总结；另一方面可以保证 token 消耗的高效性，以及去除部分对话噪音（例如部署的方式、临时问题的咨询询问等）

**2、项目调试：**
- **1）AI 自测**：建立在完善详尽的需求开发文档的基础上，AI完全可以自我实现项目的功能测试，因此在测试过程中可以要求其在交付前，自己将所有的业务功能流程进行测试验证，完成至少 3 次验证无误后才可以通过测试交付；（在验证前端样式的过程中，可以开放控制权限，让AI自己在终端运行项目，并访问对应的本地地址去阅读前端代码&借助多模态的能力校验设计稿和实施页面的差异点，并让 ai 自己进行调整；）
- **2）人工测试**：可以对照需求文档、当期版本的核心点，进行整体功能的走查工作，并针对走查出的问题进行记录整理，将当次需求内的问题丢给 ai 修复，发现的新的问题可以记录放在后续版本迭代，否则可能会陷入问题越改越多、越扣越细的困局中。

**3、项目部署**
- **1）静态页面（文本展示）**：目前个人的 blog 的页面涉及少量的数据处理定时任务 + 长期展示的静态文本页面，因此选择免费的 github 托管页面，不需要购买自己的域名&自己的服务器进行部署，等后续这些都准备妥当后可以进行迁移。（此地址不具有品牌心智 & 地址较为复杂，因此仅作为暂时使用）
- **2）动态页面（含接口交互服务等）**：计划中，后续会持续更新；
